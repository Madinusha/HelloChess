### Фактор 2. Зависимости

**Соответствует.**

- Манифест зависимостей — `pom.xml`.
- Версия Spring Boot зафиксирована через `spring-boot-starter-parent:3.3.2`, который через BOM управляет версиями всех стартеров, Jackson, PostgreSQL-драйвера, Lombok, Hibernate и др.
- Версия целевой JVM зафиксирована свойством `java.version=17`.
- Версия сборщика зафиксирована через Maven Wrapper (`.mvn/wrapper/maven-wrapper.properties`, Maven 3.9.6).
- Сборка воспроизводима командой `./mvnw clean package`.
- Приложение собирается в fat jar, включающий все runtime-зависимости, что исключает неявные зависимости от системных библиотек.

### Фактор 3. Конфигурация

**Соответствует.**

Все настройки, специфичные для среды, вынесены в переменные окружения:

```yaml
spring:
  datasource:
    url: ${DB_URL:jdbc:postgresql://localhost:5432/postgres}
    username: ${DB_USERNAME:postgres}
    password: ${DB_PASSWORD:root}
server:
  port: ${SERVER_PORT:8080}
```
Секреты в env.

### Фактор 4. Сторонние службы

**Соответствует.**

PostgreSQL рассматривается как подключаемый ресурс, доступный по URL. Внутри Docker Compose адрес БД задаётся через имя сервиса (`db:5432`), а не через `localhost`. Приложение не знает, где физически находится БД, — оно получает её адрес через переменную окружения `DB_URL`. Замена локальной БД на внешнюю (managed PostgreSQL) выполняется сменой значения переменной без изменения кода.

### Фактор 5. Сборка, релиз, запуск

**Соответствует.**

- **Build.** Сборка выделена в отдельный воспроизводимый шаг: `./mvnw clean package` создаёт fat jar. В `Dockerfile` используется multi-stage build: на первой стадии Maven собирает jar, на второй формируется минимальный runtime-образ.
- **Release.** Релиз формируется как Docker-образ `hellochess:<version>` с уникальным тегом, совпадающим с версией в `pom.xml`.
- **Run.** Запуск выполняется командой `docker compose up -d`. Конфигурация, специфичная для среды, передаётся через переменные окружения. Один и тот же образ запускается в dev, stage и prod без пересборки.

### Фактор 6. Процессы

**Соответствует.**

Приложение спроектировано как stateless-процесс:

- Данные пользователя хранятся в PostgreSQL
- HTTP-сессии хранятся в PostgreSQL через `spring-session-jdbc` 
- Запись на локальный диск отсутствует 
- Spring-бины не содержат изменяемых полей

(не относится к классам, которые мы не рассматриваем - клссы отвечающие за саму игру)
Приложение может быть остановлено и перезапущено в любой момент (`docker compose restart app`) без потери данных.

### Фактор 8. Параллелизм

**Соответствует.**

Приложение состоит из одного типа процесса — **web** (обработка HTTP-запросов и WebSocket-соединений). Фоновые (worker) и cron-процессы в доменной области отсутствуют: приложение не выполняет отложенных задач, обработки очередей или периодических операций по расписанию.

Процесс является сущностью первого класса: каждый запуск `java -jar app.jar` (или `docker run hellochess:1.0.0`) создаёт независимый процесс. Отсутствует «главный» процесс, от которого зависят остальные.

Web-процесс является stateless

---

### Фактор 9. Утилизируемость

**Соответствует.**

- **Быстрый старт.** Spring Boot приложение стартует за несколько секунд. Время старта не зависит от внешних условий (кроме доступности БД, которая проверяется healthcheck'ом).
- **Корректное завершение.** Spring Boot по умолчанию обрабатывает `SIGTERM`: закрывает входящие соединения, дожидается завершения активных запросов, корректно закрывает пул соединений с БД. В `docker-compose.yml` для `app` задано `restart: unless-stopped`.
- **Устойчивость к падению.** Процесс stateless: при внезапном завершении (`docker compose kill app`) данные не теряются, так как хранятся в PostgreSQL. При перезапуске приложение восстанавливает работоспособность.

После перезапуска пользователи могут продолжить работу (сессии хранятся в БД).

### Фактор 11. Логи (Logs)

**Соответствует.**

Приложение пишет логи исключительно используя SLF4J

- Файловые аппендеры не используются: в проекте отсутствует `logback-spring.xml` с `FileAppender`.
